# Repository README style

Write for an engineer inspecting the code. Use first person for personal decisions and "we" for shared work. Credit agents and human review separately. Short sentences, concrete constraints, no hype, badges, contribution cards or invented impact numbers.

Use the TEMPLATE headings in order, including in short archive-project drafts. Link back to the matching site page; the website repository links to the homepage. A site archive entry does not mean the GitHub repository is archived.

Say what is true and leave out what you can't verify. Don't hedge about it, and don't list what wasn't run. Only include a command that the repository's own README or scripts support. Do not promote a planned feature into a working one. Do not copy secrets, private hostnames, client identities or client repository associations.

The five projects with a case study on the site (Keeper, Keystone, lyfe, dgx-autonomy and this website) follow the same story as their site page: the problem, how it works, and where a model is used and where it isn't. Keeper is private; its draft is the opening of that repository's own README. Keystone's README is written for its developers, so it has no draft here; the site's case study is its public story.
